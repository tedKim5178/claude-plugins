# 구현 검증 체크리스트

같은 세 가지 관점을 **두 시점**에 적용한다. 코드가 없는 분석 단계에서 "구현에 반영되었는가"를 물을 수는 없으므로,
분석 단계는 *계획이 이 관점을 담고 있는가*를, 리뷰 단계는 *코드가 실제로 그렇게 되었는가*를 본다.

| 관점 | 분석 단계 (analyze-spec / analyze-bts) | 리뷰 단계 (spec-conformance-reviewer / impl-reviewer) |
|------|---------------------------------------|------------------------------------------------------|
| 1. 스펙 → 구현 일치 | 원문의 요구가 빠짐없이 todo로 쪼개졌고, 각 todo의 `acceptance`에 값·문구·조건이 원문 그대로 있는가 | diff가 각 todo의 acceptance를 충족하는가, 명시되지 않은 동작이 추가되지 않았는가 (spec-conformance) |
| 2. 실행 범위 일치 | 각 todo의 `acceptance`에 **트리거**(진입 시 / 최초 1회 / 탭 시 / 상태 변경마다)가 적혀 있는가 | 코드의 실행 조건·구독 메커니즘이 그 트리거보다 자주/넓게 발동하지 않는가 (spec-conformance) |
| 3. AS-IS 보존 | 변경 지점을 공유하는 다른 상태·서비스 타입·화면·`when` 분기를 **열거**했는가 (code-researcher 매핑표의 "같이 흔들리는 곳") | 열거된 경로 각각에서 기존 동작이 유지되는가 (impl-reviewer) |

## 분석 단계 — 리포트 출력 형식

```markdown
## ✅ 계획 검증

### 요구 → todo 대응
| 원문 요구 (출처) | todo | 비고 |
|-----------------|------|------|
| {요구 1} (댓글 #3) | T1 | |
| {요구 2} (본문) | — | ⚠️ todo 없음 → 범위 외인지 결정 필요 |

### 트리거
| todo | 트리거 | 출처 |
|------|--------|------|
| T1 | 좌석 목록 진입 시 1회 | 기획서 본문 |

### 영향 범위 (AS-IS 보존 대상)
| 경로/케이스 | 변경 지점과의 관계 | 유지되어야 할 동작 |
|------------|------------------|------------------|
| {다른 서비스 타입} | 같은 `when` 분기 | 뱃지 없음 |
```

**요구가 todo에 대응되지 않거나 트리거가 원문에 없으면 `open_questions`로 올린다.** 임의로 메우지 않는다.

## 리뷰 단계

각 리뷰어 에이전트 정의에 해당 관점의 절차와 출력 형식이 있다. 이 파일은 분담 기준만 정한다.
